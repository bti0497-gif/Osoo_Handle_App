# 플랫폼 전환 방향과 의사결정 게이트

> 이 문서는 1.x 현장관리자 앱을 안정화하는 동안, 이후의 2.x 전환 논의가 매번 처음부터 시작되지 않도록 남기는 **방향 문서**다.
>
> 실행 코드·릴리즈 계약·현장 설정을 바꾸는 문서가 아니다. 아래 선택지는 1.x 안정화 완료 뒤 별도 승인과 PoC를 거쳐서만 확정한다.

## 0. 지금의 원칙

1. **1.x의 최우선 목표는 현장 업무 안정화다.** 이 문서의 장기 방향 때문에 현재 Electron, 로컬 DB, 인증, 감시런처를 바꾸지 않는다.
2. 현재 현장 PC는 HMI를 위해 24시간 가동되며, 인터넷 불안정에도 입력 업무가 멈추지 않아야 한다.
3. 현장·사용자·권한은 분리해서 관리하는 방향을 유지한다. 업무 데이터의 현장 구분은 항상 `site_id`를 기준으로 한다.
4. 현장 앱에서 확인된 안정화 정책(로컬 저장 우선, 동기화 후속 처리, 비밀번호 비보관, 토큰 기반 세션 복원)은 전환 후에도 보존한다.

## 1. 목표 운영 구조

```text
중앙 운영 서비스
 ├─ 사용자·역할·현장 배정·권한
 ├─ 업무 규칙·검증·현장 설정·보고서 양식
 ├─ 중앙 데이터·감사 이력·진단 분석
 └─ 배포 가능한 설정/업무 모듈

현장 단말
 ├─ 업무 화면 (WinForms 또는 브라우저 기반)
 ├─ 최소 오프라인 저장·전송 대기열
 ├─ HMI/장비/파일 등 Windows 현장 연동
 └─ 중앙 서버 연결 복구

원격 지원 계층 (별도 운영 도구)
 └─ RustDesk 등 승인된 원격 접속 도구 — 중앙 앱과 권한·접속 이력만 연계 검토
```

중앙 서버에 업무 규칙과 데이터를 두면, 규칙·권한·현장 배정·양식 변경은 전체 현장에 즉시 반영할 수 있다. 단, UI와 현장 장비 연동은 각 단말의 안정적인 클라이언트 책임으로 유지한다.

### 로컬 우선 업무 실행 계약

2.x의 고성능화는 단순 메모리 캐시가 아니라 **영구 로컬 저장과 원격 동기화의 분리**를 뜻한다.

```text
업무 화면
  ↓ 로컬 IPC 또는 동등한 내부 계약
현장 업무 데이터 계층
  ├─ SQLite 즉시 저장
  ├─ 사진 로컬 파일 보존
  └─ 내구성 있는 전송 대기열
       ↓ 백그라운드 동기화
중앙 API·BigQuery·Drive
```

- 검침값·재고·수질·운전상태 입력은 로컬 저장 완료 시 현장 업무의 저장 완료로 본다.
- 원격 전송 성공 여부는 사용자 입력 완료 여부와 분리하며, 실패 시 업무를 막지 않고 재시도 상태와 진단을 남긴다.
- 사진은 파일 존재·해시·현장·업무일·종류를 로컬에서 먼저 확정한 뒤 전송한다.
- 전송 대기열은 `site_id`, 사용자, 작성 시각, 순서, 중복 방지 키, 재시도 횟수와 최종 오류를 보존한다.
- 인증·권한·현장 귀속을 복원하기 전에는 대기 요청을 재전송하지 않는다.
- 삭제, 설정, 권한 변경처럼 자동 재시도가 위험한 작업은 일반 입력과 분리하고 사용자 확인 또는 별도 보상 규칙을 둔다.
- 로컬 데이터 계층의 단일 writer를 보장하며 Electron 렌더러, 로컬 서버, Windows 서비스가 같은 SQLite를 경쟁적으로 쓰지 않는다.
- 기존 로컬 Express 서버는 PoC 결과에 따라 동기화 전용으로 축소하거나 제거할 수 있지만, 1.x 안정화 중에는 역할을 바꾸지 않는다.
- 전환은 유량 등 한 업무의 선택 현장 PoC부터 시작하며 기존 1.x 경로와 결과가 일치하는지 검증한 뒤 점진적으로 확대한다.

## 2. 2.x에서 비교할 클라이언트 선택지

| 선택지 | 강점 | 주의점 | 적합한 역할 |
| --- | --- | --- | --- |
| WinForms + 중앙 API | Windows/HMI·파일·장비 연동, 견고한 그리드 | 화면 변경은 클라이언트 배포 필요 | 현장 업무 단말 |
| 브라우저 SaaS + 오프라인 보조 | UI·업무 규칙의 즉시 배포, 사용자 교체·현장 배정 용이 | 오프라인·장비 연동을 별도 설계해야 함 | 중앙관리와 표준 업무 화면 |
| 혼합형 | 중앙 API/권한/데이터를 공유하며 필요 화면만 네이티브화 | 경계·버전 계약을 먼저 고정해야 함 | 가장 현실적인 단계 전환 후보 |

현재 결정은 **보류**다. 먼저 중앙 API 계약과 오프라인 보조 정책을 확정한 뒤, 일지·그리드·HMI 연동 PoC 결과로 선택한다.

## 3. 문서·출력물 방향

- HWPX는 공개 XML 기반의 보관·제출용 원본 형식으로 단계 전환을 검토한다.
- 현장 업무 흐름은 한글(HWP) 프로그램 실행에 의존하지 않는 것을 목표로 한다.
- 앱의 기본 미리보기·인쇄는 PDF 또는 앱 내 렌더링으로 제공하고, HWPX는 다운로드 원본으로 제공한다.
- 첫 대상은 표·숫자 중심의 일일업무일지다. 고급 한글 서식은 HWPX 호환성 PoC로 먼저 검증한다.

## 4. 원격 관제 확장 방향

- HMI 감시 화면은 기존 운영 체계를 유지한다.
- 중앙관리 앱은 장기적으로 현장 상태·업무 현황·알림·원격 접속 진입점을 제공할 수 있다.
- RustDesk 등의 원격 도구를 앱에 내장하거나 대체하지 않는다. 현장별 권한, 접속 이력, 승인, 비상 차단 기준이 정리된 뒤 연동만 검토한다.
- 최초 단계는 보기·지원 목적이며, HMI 조작 권한은 별도 정책과 통제를 전제로 한다.

## 5. Windows 서비스 전환의 0단계와 감시런처 1.0.5 후보

Windows 서비스 전환은 업무 API를 포트별로 나누어 동시에 운영하지 않는다. 동일한 SQLite·인증·`site_id` 컨텍스트를 두 서버가 함께 소유하면 세션 불일치와 DB 잠금 위험이 생긴다.

대신 1.x 이후의 별도 승인 작업에서 다음 **무영향 관찰 단계**를 먼저 검증한다.

```text
기존 Electron 서버 : 18731, 모든 실제 업무·SQLite·인증을 단독 소유
시험 Windows 서비스 : 별도 loopback 포트, 상태 응답만 제공, 업무·DB·인증 미사용
감시런처 1.0.5 후보 : 두 프로세스의 생명주기와 연결 상태를 독립 기록
```

감시런처 1.0.5 후보 역할:

- Electron 앱과 시험 서비스의 PID, 버전, 가동 시간, 포트 소유, loopback 상태 응답, 시작·중지·재시작 이력을 한 타임라인으로 기록한다.
- 서비스가 정상이고 앱이 정상인지, 서비스만 멈췄는지, 앱만 멈췄는지, 통신만 실패했는지를 구분한다.
- 이 단계에서는 기존 18731 서버·업무 API·SQLite·로그인 세션을 재시작하거나 변경하지 않는다. 관찰 실패도 업무를 차단하지 않고 진단으로만 남긴다.
- 서비스 상태 API에는 비밀번호, 토큰, DB 내용, 현장 업무 데이터를 포함하지 않는다.
- Windows 서비스 관리자는 서비스 복구를, 감시런처는 앱 및 서비스 상태 관찰을 담당한다. 둘이 서로의 프로세스를 경쟁적으로 종료·재시작하지 않는다.

0단계의 설치·자동 시작·권한·업데이트·서비스 복구가 실제 현장 PC에서 충분히 검증된 뒤에만, 선택 현장에서 서비스가 기존 18731 업무 서버의 소유권을 받는 다음 단계로 진행한다.

## 6. 전환 시작 게이트

아래 조건이 충족되기 전에는 2.x 구현을 시작하지 않는다.

1. 1.x 안정화 버전이 현장 진단로그에서 반복적인 앱 중단·세션 손실·복구 실패 없이 충분한 기간 운영된다.
2. 현장별 Windows·메모리·디스크·감시런처 기준선이 수집되어 있다.
3. 중앙 API의 인증, `site_id`, 권한, 데이터 소유권 계약이 문서화된다.
4. 오프라인 상태에서 입력·사진·서명·동기화가 어떻게 보존·재전송되는지 PoC로 검증된다.
5. 일일업무일지 HWPX/PDF 생성 및 브라우저 미리보기 PoC가 기존 양식의 핵심 표·수치와 일치한다.
6. 선택한 클라이언트의 설치·업데이트·롤백·현장 권한 환경을 실제 PC에서 검증한다.
