# 현장관리자 앱 감시 런처 개발 계획

작성일: 2026-08-01  
대상 저장소: `E:\Wastewater Treatment Plant`  
대상 앱: Osoo Handle App (현장관리자용 Electron 앱)

## 1. 목적

현장 PC는 대체로 계속 켜져 있고 HMI 화면도 상시 표시한다. 따라서 앱 창을 닫았거나 일시적으로 창이 사라진 경우에도 로컬 Express 서버, 로그인 세션, 메뉴 그리드 캐시를 가능한 한 유지해야 한다.

다만 다음 경우에는 Electron 프로세스 자체가 사라질 수 있다.

- 작업 관리자에서 강제 종료
- 런타임 오류/비정상 종료
- Windows 업데이트 또는 사용자 로그아웃 후 재로그인

이를 보완하기 위해 앱 본체와 별도로 동작하는 아주 작은 **감시 런처(Watchdog)** 를 둔다. 감시 런처는 앱이 없을 때만 백그라운드 트레이 모드로 재시작한다.

## 2. 절대 지켜야 할 원칙

1. 감시 런처는 Windows 서비스(LocalSystem)가 아니다.
   - 앱의 SQLite DB, 토큰, 설정은 현재 사용자 `%APPDATA%\Osoo_Handle_App`에 있다.
   - 감시 런처도 반드시 현재 로그인한 사용자 권한으로 실행한다.
2. 앱 본체와 감시 런처의 버전/배포 주기를 분리한다.
   - 일반 앱 릴리즈는 감시 런처 파일과 작업 스케줄러를 건드리지 않는다.
   - 감시 런처 자체를 고칠 때만 별도 런처 버전을 올려 교체한다.
3. 일반적인 창 닫기는 앱 종료가 아니라 트레이 숨김이어야 한다.
4. 사용자의 명시적 **완전 종료** 및 앱 자동 업데이트 중에는 감시 런처가 앱을 다시 띄우면 안 된다.
5. 감시 기능이 데이터 저장/동기화/로그인을 대신 수행하면 안 된다. 오직 앱 본체의 생존 여부와 재기동만 관리한다.
6. DB 경로는 계속 `%APPDATA%\Osoo_Handle_App\osoo.db`이며, Program Files에 데이터를 만들지 않는다.

## 3. 현행 관련 구조

- Electron 진입점: `electron/main.cjs`
- 업데이트 처리: `electron/updater.cjs`
- 설치 설정: `electron-builder.config.cjs`
- 통합 설치 스크립트: `scripts/build-integrated-installer.ps1`
- 앱 서버 포트: `18731` (현재 전용 포트 회수 로직 존재)
- 앱 데이터: `%APPDATA%\Osoo_Handle_App`
- 업데이트 대기 파일 예: `%LOCALAPPDATA%\wastewater-treatment-plant-updater\pending\...`
- 현재 Electron은 `--osoo-background-start` 인수로 창을 숨긴 백그라운드 시작을 지원한다.

현재 `main.cjs`의 서버 가드는 Electron 본체가 살아 있을 때만 유효하다. Electron이 사라지면 가드도 함께 종료되므로, 외부 감시 런처가 필요하다.

## 4. 권장 구성

```text
현재 사용자 로그인
  └─ Windows 작업 스케줄러: Osoo Handle App Watchdog
       └─ OsooWatchdog.exe (또는 동일한 역할의 작고 독립된 실행 파일)
            ├─ 본체 프로세스 존재 → 대기
            ├─ 본체 없음 + 정비 잠금 없음 → 10~15초 후 본체를 트레이 모드로 실행
            ├─ 본체 없음 + 정비 잠금 유효 → 대기
            └─ 같은 런처 중복 실행 → 즉시 종료

Osoo Handle App.exe
  ├─ 일반 X/트레이 닫기 → 창 숨김, 서버/캐시 유지
  ├─ "완전 종료" → 정비 잠금 작성 후 본체 종료
  └─ 자동 업데이트 → 업데이트 잠금 작성 후 본체 종료
```

### 4.1 런처 구현 선택

권장: **Windows 7 SP1 호환 Win32 네이티브 실행 파일** `OsooWatchdog.exe`.

- Electron을 다시 하나 띄워 감시자로 쓰지 않는다. 메모리 절약 목적에 맞지 않는다.
- 단순 `.bat`/PowerShell 무한 루프는 실행 정책, 콘솔 창, 오류 복구, 중복 실행, 업데이트 교체 관리가 취약하므로 운영용으로 쓰지 않는다.
- 소스는 새 폴더 `watchdog/`에 두고, 빌드 산출물만 앱 설치 구성품으로 포함한다.
- 감시 런처가 외부 네트워크/Google/BigQuery에 접근해서는 안 된다.

### 4.2 Windows 7 공용 플랫폼 호환성 (필수)

감시 런처는 Windows 10/11 전용으로 만들면 안 된다. 기존 현장에 Windows 7이 있을 수 있으므로 **Windows 7 SP1 이상, Windows 10, Windows 11의 공용 실행 파일**을 목표로 한다.

- 우선 선택: Visual C++/Win32 API 기반의 작은 네이티브 EXE.
- 타깃은 Windows 7 SP1(`_WIN32_WINNT=0x0601`)으로 고정하고, Windows 8/10 전용 API를 사용하지 않는다.
- 보조 선택: .NET Framework 4.7.2 이하 대상. **.NET 6/8 self-contained 단일 파일은 Windows 7 지원 대상으로 채택하지 않는다.**
- x64 현장은 x64 EXE를 쓰되, Windows 7 32비트 현장 가능성이 있으면 x86 빌드도 함께 준비하거나 사전 조사한다.
- PowerShell 버전, Windows Terminal, 최신 Task Scheduler API에 의존하지 않는다. 기본 `schtasks.exe`/Win32 Task Scheduler 기능으로 충분해야 한다.
- 콘솔 창이 나타나지 않게 GUI subsystem으로 빌드하고, 파일/레지스트리/작업 스케줄러 오류를 자체 순환 로그에 남긴다.

중요: 감시 런처가 Windows 7에서 동작하더라도 **앱 본체(Electron)의 해당 버전이 Windows 7에서 실행 가능한지**는 별도 문제다. 본체의 Electron/Chromium 버전과 설치기(NSIS) 호환성을 반드시 확인한다. 본체가 지원하지 않는 환경에서 런처만 재시작을 반복하지 않도록, 실행 실패 시 반복 크래시 방지 쿨다운을 적용한다.

## 5. 파일 및 상태 계약

모든 런타임 상태는 다음 폴더에 둔다.

```text
%APPDATA%\Osoo_Handle_App\runtime\
  watchdog.lock                 # 감시 런처 단일 인스턴스 잠금
  maintenance.json              # 의도된 완전 종료/업데이트 잠금
  watchdog-status.json          # 선택: 마지막 검사/실행/오류 상태
  watchdog.log                  # 크기 순환 로그
```

`maintenance.json` 예시:

```json
{
  "reason": "update",
  "createdAt": "2026-08-01T01:00:00.000Z",
  "expiresAt": "2026-08-01T01:15:00.000Z",
  "requestedBy": "app"
}
```

규칙:

- `reason`: `update`, `full-exit`, `installer`, `maintenance` 중 하나.
- `expiresAt`가 지난 잠금은 런처가 자동 무시/삭제한다. 영구 잠금으로 앱이 다시 살아나지 않는 상태를 막는다.
- 자동 업데이트용 잠금은 15분 정도로 충분하다. 설치 성공 뒤 새 앱이 기동하면 즉시 지운다.
- 사용자가 선택한 완전 종료는 기본 8시간 잠금으로 두되, 다음 Windows 로그인/앱 수동 실행 시 해제할 수 있도록 한다. 이 정책은 구현 전 현업 확인 필요.
- 잠금/상태 파일에는 비밀번호, 토큰, Google 자격증명, 사용자 개인정보를 기록하지 않는다.

## 6. 동작 정책

### 6.1 정상 사용

| 상황 | 앱 본체 | 감시 런처 |
|---|---|---|
| 창 X 클릭 | 창 숨김, 트레이 상주 | 아무 작업 없음 |
| 트레이 아이콘 더블 클릭 | 창 복원 | 아무 작업 없음 |
| 트레이 메뉴 `완전 종료` | 잠금 작성 후 종료 | 유효 잠금 동안 재시작하지 않음 |
| 작업 관리자 강제 종료 | 프로세스 소멸 | 10~15초 안정 대기 후 `--osoo-background-start` 재기동 |
| 렌더러/서버 오류로 본체 종료 | 프로세스 소멸 | 동일하게 재기동 |
| Windows 로그인 | 초기 본체 없음 | 백그라운드 트레이 모드로 기동 |

### 6.2 업데이트

1. `electron/updater.cjs`가 설치 직전 `maintenance.json`을 `reason: update`로 작성한다.
2. 앱 본체가 종료된다.
3. 감시 런처는 잠금이 유효한 동안 재기동하지 않는다.
4. NSIS 설치기가 앱 본체를 교체한다.
5. 새 앱 본체가 기동되면 업데이트 잠금을 삭제한다.
6. 설치 실패나 재부팅으로 새 앱이 기동하지 못한 경우에는 잠금 만료 뒤 감시 런처가 기존/새 실행 경로를 한 번 재시도한다.

**금지:** 업데이트 중 감시 런처가 앱을 즉시 되살려 설치기의 파일 교체를 방해하는 동작.

### 6.3 반복 크래시 방지

런처는 무한 재시작 루프를 만들면 안 된다.

- 최근 10분 내 재기동이 3회를 넘으면 30분 쿨다운.
- 쿨다운 중에는 `watchdog-status.json`과 순환 로그에 원인을 남긴다.
- 사용자가 수동으로 앱을 실행하면 쿨다운을 해제할 수 있다.
- 장기 실패 시 Windows 알림 또는 트레이 알림을 한 번만 표시한다. 콘솔 창을 띄우지 않는다.

## 7. 앱 본체 수정 범위

### `electron/main.cjs`

- 일반 창 닫기 이벤트는 `preventDefault()` 후 창 숨김 처리 확인/보강.
- 트레이 메뉴에 명확한 `창 열기`, `완전 종료` 항목을 둔다.
- `완전 종료`에서 maintenance 잠금 작성 후 `app.quit()`.
- `--osoo-background-start` 기동 시 창은 숨기되 서버는 시작하고 트레이 아이콘은 즉시 만든다.
- 정상 기동 성공 후 만료되지 않은 `reason: update` 잠금을 삭제한다.
- 앱 시작/종료/트레이 복원 및 서버 준비 시간을 진단 로그에 남긴다. 비밀값은 기록 금지.

### `electron/updater.cjs`

- `quitAndInstall` 직전에 `reason: update` 잠금 작성.
- 설치 시작 실패 시 잠금을 삭제하거나 짧은 만료로 바꾼다.
- 현재의 machine-wide/elevated update 정책(`c151445`)과 충돌하지 않게 한다.

### 설치 설정

- 일반 앱 업데이트에서는 감시 런처를 복사/교체/재등록하지 않는다.
- 감시 런처 버전이 변경된 릴리즈에서만 NSIS가 아래 순서를 수행한다.
  1. 감시 런처 종료 요청
  2. 새 런처 파일 교체
  3. 현재 사용자 작업 스케줄러 확인/갱신
  4. 새 런처 시작
- 런처 버전은 별도 파일(예: `watchdog-version.json`)로 관리한다.
- 런처의 설치 경로는 안정적인 고정 경로를 사용한다. 권장 경로:
  `%ProgramData%\OsooHandleApp\watchdog\OsooWatchdog.exe`
  - 앱 본체가 Program Files에 설치되더라도, 런처 업데이트를 분리하기 쉽다.
  - 단, ProgramData 쓰기는 설치기 상승 권한에서만 수행한다.

### 작업 스케줄러

- 이름: `Osoo Handle App Watchdog`
- 트리거: 현재 사용자 로그온 시.
- 실행 계정: 현재 사용자, 대화형 세션.
- 관리자 계정/LocalSystem으로 실행 금지.
- 중복 실행 정책: 기존 인스턴스가 이미 실행 중이면 새 인스턴스를 실행하지 않음.
- 등록 실패는 앱 기능을 막지 않고 진단 로그와 설정 화면 상태에만 표시.

## 8. 감시 런처 의사 코드

```text
acquireSingleInstanceLock()
resolve app executable path

loop every 5 seconds:
  if maintenance lock is valid:
    continue
  if app process exists:
    reset crash counter
    continue
  if app executable does not exist:
    log and wait
    continue
  if restart threshold exceeded:
    log cooldown and wait
    continue

  wait 10 seconds (process race 방지)
  re-check process and maintenance lock
  if still absent:
    launch app with --osoo-background-start
    record restart timestamp
```

프로세스 이름만으로 판단하지 말고, 가능하면 실행 파일의 절대 경로와 현재 사용자 세션도 함께 검사한다. 다른 PC 사용자/다른 설치본의 동일 EXE를 오인하면 안 된다.

## 9. 캐시 및 성능과의 연결

현재 앱에는 다음 캐시 개선 커밋이 있다.

- `b7430ba perf: warm grid and board caches in background`
  - 유량/약품/수질/키트/운전상태/설정을 두 개씩 예열
  - 10분 주기 및 창 복귀 시 갱신
  - 소통게시판 사전 예열 및 짧은 캐시

감시 런처는 앱 프로세스가 유지되는 동안 이 메모리 캐시를 보존하게 한다. 앱이 강제 종료되어 재시작된 경우에는 캐시가 초기화되는 것이 정상이며, 앱의 예열 로직이 다시 채운다.

대용량 전체 데이터의 별도 캐시 DB 복제는 금지한다. SQLite가 이미 원본 저장소이고, 별도 캐시는 최신성/무효화 위험을 늘린다.

## 10. 구현 단계

### 1단계 — 설계/기반

- 런처 프로젝트 생성 및 단일 파일 빌드 자동화.
- `runtime` 경로와 maintenance 잠금 유틸리티를 앱/런처가 공유하도록 계약 확정.
- 앱의 일반 닫기와 완전 종료 동작을 명확히 분리.
- 수동으로 런처를 실행하여 재기동/잠금/중복 실행 단위 테스트.

### 2단계 — 설치 통합

- 첫 감시 런처 포함 릴리즈에서만 런처와 작업 스케줄러를 설치.
- 설치/업데이트/제거 시나리오를 NSIS에서 검증.
- 제거 시 작업 스케줄러와 ProgramData 런처만 삭제하고 `%APPDATA%\Osoo_Handle_App` 데이터는 사용자 확인 없이 삭제하지 않는다.

### 3단계 — 운영 안정화

- 재시작 횟수/사유/시간을 제한된 크기의 로컬 로그로 기록.
- 다음 진단 로그 전송에 요약만 포함.
- 반복 크래시/업데이트 충돌/잠금 만료를 실제 현장 PC에서 점검.

- [ ] 업데이트 성공 후 새 본체가 기동하고 update 잠금이 지워지는가?

## 12. 릴리즈 정책

1. **첫 도입 릴리즈**
   - 앱 릴리즈와 함께 Watchdog `1.0.0` 포함.
   - 설치판 전체 검증 후 제한된 현장부터 배포.
2. **일반 앱 릴리즈**
   - 감시 런처 버전/파일/스케줄러는 불변.
   - 앱 본체만 업데이트.
3. **감시 런처 변경 릴리즈**
   - Watchdog 버전만 별도 증가.
   - 설치기가 런처를 중지·교체·재시작.
   - 앱 본체 변경이 없어도 전용 설치판 검증 필요.

# 현장 앱 본체 안정화 병행 계획

감시 런처는 앱이 사라졌을 때 복구하는 장치일 뿐이다. 데이터가 잘못 저장되거나 메뉴가 느리거나 업데이트가 꼬이는 문제는 앱 본체에서 해결해야 한다. 아래 항목은 감시 런처 개발과 함께 진행한다.

## A. 데이터 식별자 정책: `site_id` 우선

### 원칙

- 내부 조회·저장·수정·삭제·BigQuery 동기화의 기준은 불변값 `site_id`.
- `site_name`은 화면 표시, 출력 문서 제목, Drive 파일명에만 사용.
- 현장명 변경/띄어쓰기/방향 표기 차이로 조회가 누락되면 안 된다.
- `site_id`는 로그인 자격을 판단하는 값이 아니라 로그인 이후 운영 데이터의 현장 범위를 정하는 값이다.
- 관리자 로그인과 현장 설정/복구는 site_id가 없거나 잘못된 상태에서도 접근 가능해야 한다.

### 점검 대상

- 로컬 SQLite 모든 운영 테이블
- BigQuery 업로드/복원 쿼리
- 수질·유량·약품·키트·운전상태·출퇴근·사진·일지·성적서
- 다중/양방향 현장 창의 `x-osoo-site-id` 헤더 처리
- 도로공사 서버 과거자료 복원 결과의 site_id 매핑

### 구현/검증

- API 라우트별로 `site_id`가 없을 때 실패시키거나, 명시적으로 호환 보정하는지 표로 점검.
- `app_settings.site_id`와 선택 현장(`sites.id`)의 일치 여부를 시작 진단에 기록.
- 저장 직후 해당 행의 site_id가 현재 선택 현장과 일치하는지 개발/진단 모드에서 검증.
- 현장명만 다른 테스트 데이터로도 다른 현장 데이터가 섞이지 않는 회귀 테스트 작성.

## B. 시간·날짜 정책: KST를 업무 기준으로 고정

### 구분

| 데이터 종류 | 저장 기준 | 화면/문서 기준 |
|---|---|---|
| 업무일자(유량, 약품, 수질, 일지, 출결 날짜) | KST `YYYY-MM-DD` 문자열 | KST |
| 실제 발생 시각/생성·수정·동기화 시각 | UTC ISO timestamp | KST로 변환 표시 |
| BigQuery 시간 범위 조회 | KST 경계를 UTC로 환산 | KST 날짜 선택 |
| Excel 날짜 셀 | UTC 정오 Date 또는 문자열 | KST 날짜가 전날로 밀리지 않아야 함 |

### 금지 패턴

- 업무일자에 `new Date('YYYY-MM-DD')` 사용 금지.
- 업무일자 생성에 `toISOString().slice(0, 10)` 사용 금지.
- KST 자정의 JavaScript `Date`를 ExcelJS 날짜 셀에 직접 전달 금지.

### 점검 대상

- 월운영보고서 (`monthlyOperationReportService.cjs`의 UTC 정오 보정 유지)
- 일일/월간 일지, 출결, 수질분석일지, 성적서, Drive 파일명, BigQuery 복원 기간
- 자정 전후(23:50~00:10 KST) 자동 동기화와 날짜 필터

## C. 시작 속도와 메뉴 성능

### 이미 적용된 개선

- `b7430ba`: 그리드 데이터 두 개씩 백그라운드 예열, 10분 주기/창 복귀 시 갱신, 소통게시판 사전 예열/짧은 캐시.

### 추가 개선 후보 (측정 후 적용)

1. Electron 창/스플래시를 서버 준비 전에 먼저 보이게 해 체감 대기 감소.
2. `electron/main.cjs`의 포트 회수 PowerShell을 매 시작마다 동기 실행하지 말고:
   - 짧은 포트 탐색 먼저 수행
   - 실제 점유 상태일 때만 회수 스크립트 실행
3. `serverConfig.js`의 같은 포트에 대한 중복 ping을 하나의 제한된 재시도로 통합.
4. 로그인 후 서버 세션 복구가 끝난 다음 게시판 API를 호출하도록 해 초기 `ACTIVE_SESSION_REQUIRED`(401) 경쟁 상태 제거.
5. 메뉴 번들은 사용 빈도 순으로 idle 시간에 미리 import하되, 한꺼번에 모두 파싱하지 않는다.
6. 매우 큰 그리드는 가상 스크롤/페이지 단위 렌더링을 검토한다. 단, 데이터 자체를 임의 `slice()`하여 누락시키면 안 된다.

### 측정 기준

각 단계의 KST/UTC 기준 경과 시간을 진단 로그에 숫자로 기록한다.

```text
electron-ready
window-created
server-port-probe
server-ready
session-restored
dashboard-visible
grid-cache-warm-start/end
board-cache-warm-start/end
```

로그는 시작마다 한 번의 요약 이벤트만 남긴다. 요청별 과다 로그나 민감정보 기록은 금지한다.

## D. 로컬 DB 안정성

- DB 경로는 항상 `%APPDATA%\Osoo_Handle_App\osoo.db`.
- 앱 버전 전환 시 마이그레이션 전 안전 백업은 유지.
- `quick_check`, 스키마 검사, 필수 테이블 검증은 제거하지 않는다.
- 대용량 `VACUUM`/복구/BigQuery 전체 동기화는 화면 진입 직후가 아니라 명시적인 작업 또는 유휴 시간에 수행.
- SQLite 원본 데이터를 브라우저/별도 캐시 DB에 중복 보관하지 않는다.
- BigQuery 복원 전 자동 DB 백업, 미동기 로컬 행 보호, 복원 결과 건수 표시는 계속 유지.

## E. 동기화·네트워크 안정성

- 로컬 저장 성공을 먼저 확정한 뒤 BigQuery/Drive는 후속 동기화.
- 네트워크 실패가 로컬 저장 성공을 실패로 표시하지 않도록 분리.
- 동기화 재시도는 지수 백오프와 최대 횟수를 둔다. 무한 재시도 금지.
- 같은 데이터의 중복 업로드를 막기 위한 행 식별자/업서트 키를 점검.
- Drive 실패 시 로컬 파일은 유지하고 화면에는 "로컬 저장 완료, Drive 전송 실패"를 명확히 표시.
- 진단 로그 전송 실패가 사용자 업무를 막지 않도록 한다.

## F. 인증·게시판 안정성

- 서버 재시작 직후에는 in-memory active session이 비어 있을 수 있다.
- `/api/auth/session`으로 세션을 복구한 뒤 게시판·알림 요청을 시작한다.
- 게시판 최초 401은 한 번만 짧게 재시도하고, 성공 시 사용자에게 경고를 표시하지 않는다.
- 토큰/비밀번호/Google credential은 진단 로그, 브라우저 콘솔, 오류 메시지에 출력 금지.

### F-1. 로그인 신뢰성: 복수 클릭이 필요하지 않아야 함

현장 복구 과정에서 로그인 버튼을 여러 번 눌러야 성공한 사례는 안정화 최우선 신호로 취급한다. 사용자 입장에서는 모두 "로그인이 안 됨"으로 보이지만, 실제 원인은 구분해야 한다.

| 가능한 원인 | 판별 방법 | 개선 방향 |
|---|---|---|
| 로컬 Express 서버 미기동/기동 지연 | `server-ready` 이전 로그인 요청, 포트 probe 결과 | 로그인 버튼을 서버 준비 전 비활성화하고 자동 대기/재시도 |
| 기존 프로세스/포트 18731 잔존 | 포트 회수 시간·PID·재시도 횟수 | 점유 시에만 회수하고, 감시 런처와 단일 인스턴스 계약 적용 |
| 서버는 떴지만 DB 마이그레이션/검사 중 | DB 준비 완료 시점과 로그인 요청 시점 비교 | 서버 readiness를 DB 준비 완료 이후에만 true로 표시 |
| 업데이트 직후 AppData/세션 초기화 | 버전, DB 경로, session restore 결과 | AppData 경로 고정·업데이트 단계별 로그·안전한 세션 복구 |
| 인증 성공 후 active session 등록 경쟁 | 로그인 응답, `/api/auth/session`, 첫 보호 API 순서 | 로그인 완료 전에 보호 메뉴 요청 금지, 단일 세션 복구 Promise 공유 |

구현 원칙:

1. **인트로 화면은 서버·DB·필수 설정·저장 세션 복구가 모두 준비되기 전까지 유지한다.** 준비되지 않은 로그인 화면을 먼저 보여주지 않는다.
2. 준비 완료 뒤에만 로그인 화면 또는 자동 로그인된 업무 화면으로 전환한다. 이것이 인트로 그래픽의 본래 역할이다.
3. 사용자가 버튼을 여러 번 눌러도 한 번의 로그인 요청만 진행되게 한다.
4. 인트로 단계에서 서버 준비가 지연되면 오류 대신 "업무 서버를 준비하고 있습니다" 상태와 자동 재발견/제한 재시도를 표시한다.
5. 재시도 끝에도 실패할 때만 인트로에서 안전한 오류 화면으로 전환하고, "서버 미기동", "DB 준비 실패", "인증 복구 실패"를 구분해 안내한다.
6. 감시 런처가 앱을 재기동한 직후에도 이 흐름이 동일하게 적용되어야 한다.

필수 진단 이벤트(비밀값 제외):

```text
app-launch
server-port-probe-start/end
server-ready
db-ready
login-clicked
login-request-start/end
login-result
active-session-set
first-protected-api-result
```

목표 기준: 정상 네트워크/정상 DB인 현장 PC에서 첫 로그인 클릭 1회로 완료되어야 하며, 서버 준비 대기는 사용자가 재시도하지 않아도 자동으로 처리되어야 한다.

## G. 업데이트 안정성

- 현재 본체 업데이트는 machine-wide/elevated 정책을 사용한다. (`c151445` 기반)
- 앱 실행은 일반 사용자 권한으로 유지하고, 설치기만 UAC 상승.
- 업데이트 상태를 `available → downloaded → install-started → new-version-started`로 기록.
- 감시 런처 도입 전후 모두 업데이트 중 재기동 방지 잠금 회귀 테스트 필수.
- 릴리즈 전에는 새 설치, 기존 버전 자동 업데이트, 업데이트 실패/재시도, 롤백 가능 여부를 각각 점검.

## H. 진단 로그 운영

- 로그는 오류 원인 분석에 필요한 최소 정보만 포함: 앱 버전, 컴퓨터 식별자 해시/현장 site_id, 이벤트명, 경과시간, 오류 코드/요약.
- 대형 Electron 서버 로그는 회전 정책 적용: 예) 파일당 10 MB, 최대 5개.
- Drive의 진단 로그는 새 릴리즈 후 일정 기간 분석하고, 분석 완료한 이전 릴리즈 로그는 정리한다.
- 운영 데이터/사진/자격증명/전체 SQL 결과를 진단 로그에 넣지 않는다.

## I. 안정화 릴리즈 절차

1. 기능 개발과 안정화 패치를 분리한 브랜치/커밋 유지.
2. 수정 파일 lint, `npm run build`, 서버 문법 검사, 네이티브 SQLite 로딩 점검.
3. 최소 1대 테스트 현장에서 다음을 확인:
   - 로그인, 유량/약품/수질 저장, BigQuery 동기화
   - 트레이 숨김/복원
   - 강제 종료 후 런처 복구
   - 게시판 진입
   - 자정 전후 날짜/일지 출력
   - 자동 업데이트
4. 제한 배포 뒤 Drive 진단 로그를 분석.
5. 오류가 없을 때 전체 현장 배포.

## J. 코파일럿 작업 순서 제안

1. 이 문서의 감시 런처 1단계(상태 계약 + 앱 완전 종료 분리)부터 구현.
2. 시작 타이밍 진단 추가 후 실제 저사양 PC의 병목 수치 확보.
3. 포트 탐색/중복 ping/게시판 세션 경쟁 상태를 작은 독립 커밋으로 수정.
4. 감시 런처 설치 통합은 현장 1대에서 수동 설치/업데이트/강제종료 테스트 후 진행.
5. `site_id` 및 시간 정책은 기능별 체크리스트를 만들어 점진적으로 전수 점검. 일괄 대규모 리팩터링은 피한다.

## K. 백엔드 라우트 교통정리 및 보호 계획

### 목표

라우트는 단순히 URL을 모아 둔 곳이 아니라 현장 앱의 데이터 안전 경계다. 새 기능을 추가하거나 한 화면을 수정할 때 기존 저장·동기화·권한 로직이 우연히 바뀌지 않도록 다음 계층을 명확히 분리한다.

```text
React Model
  → API route (입력/권한/응답 계약만 담당)
  → service (업무 규칙·트랜잭션·외부 전송 순서)
  → repository/database (SQLite SQL만 담당)
  → sync service (BigQuery/Drive 등 외부 전송)
```

### K-1. 라우트 등록을 한곳에서 확인 가능하게 유지

- 서버 진입점 `server/index.cjs`의 라우트 등록 순서를 문서화한다.
- 각 `server/routes/*.cjs`에는 책임 범위, 인증 방식, 관련 SQLite 테이블, BigQuery/Drive 부작용을 파일 상단 주석 또는 라우트 인벤토리 문서에 남긴다.
- 신규 기능은 기존 대형 라우트 파일에 무분별하게 붙이지 말고 기능별 라우트/서비스로 분리한다.
- URL 변경/제거는 금지에 가깝게 다룬다. 변경이 필요하면 기존 URL을 호환 래퍼로 일정 기간 유지한다.
- 라우트 로드 순서가 충돌할 수 있는 `/:id` 와 고정 경로(`/history`, `/sync`, `/restore` 등)는 고정 경로를 먼저 등록한다.

### K-2. 공통 보호 순서

운영 데이터 보호 대상 API는 아래 순서를 지킨다.

```text
1. 서버 토큰 검증 (x-osoo-server-token)
2. 현재 활성 사용자 세션 확인
3. 요청 입력값 형식/범위 검증
4. 현재 창의 site_id 결정 (x-osoo-site-id 또는 검증된 app_settings)
5. 권한 확인 (역할·대상 현장)
6. 서비스 호출
7. 표준 응답/진단 요약 기록
```

인증·복구 API와 운영 데이터 API를 분리한다.

| 구분 | site_id 정책 |
|---|---|
| 서버 상태 확인 | site_id 없이 허용 |
| 관리자/현장사용자 로그인 | site_id 없이 허용. 사용자 자격을 먼저 검증 |
| 저장 세션 복구 | site_id 없이 허용하되 복구 후 현장 컨텍스트 상태를 별도 확인 |
| 현장 목록 조회·최초 현장 설정·현장 변경 | site_id 없이 허용. 관리자/허용된 로컬 권한 검증 필수 |
| 유량·수질·약품·키트·슬러지·운전상태·일지 | 유효한 site_id 필수 |
| 사진·성적서·BigQuery·Drive·복원 | 유효한 site_id 필수 |

- site_id가 없거나 과거 설정과 불일치해도 로그인 자체를 차단하지 않는다.
- 현장 사용자가 로그인했지만 유효한 site_id를 확정하지 못한 경우, 로그인은 유지하고 운영 데이터 메뉴를 잠근 뒤 관리자 현장 설정 안내를 표시한다.
- 관리자는 잘못된 `app_settings.site_id`, 누락된 `sites` 행, 비활성 현장 상태를 앱 안에서 복구할 수 있어야 한다.
- site_id가 없는 운영 API를 조용히 무범위 조회로 실행하지 않는다. `SITE_CONTEXT_REQUIRED` 오류로 중단한다.

- 프론트가 보내는 현장명·역할·사용자명을 신뢰해 권한을 판정하지 않는다. 서버의 활성 세션과 site_id 기준으로 재검증한다.
- `site_id`가 필요한 운영 라우트에서 누락되었을 때 다른 현장 기본값이나 전체 현장 조회로 조용히 진행하지 않는다. 명확한 `SITE_CONTEXT_REQUIRED` 오류를 반환한다.
- 로그인 복구 직후 일시적으로 세션이 없을 수 있는 읽기 API(예: 게시판)는 프론트에서 세션 복구 뒤 호출하거나 한 번만 짧게 재시도한다. 서버 보호를 우회하지 않는다.
- 파일 경로, SQL, Drive ID, 외부 URL은 사용자 입력을 그대로 사용하지 않고 정규화/허용 목록 검증한다.

### K-3. 표준 응답·오류 계약

모든 JSON API의 성공/실패 형식을 통일한다.

```json
{ "success": true, "data": {} }
```

```json
{
  "success": false,
  "code": "SITE_ID_REQUIRED",
  "message": "개발자용 원인 요약",
  "userMessage": "현재 현장 정보를 확인한 뒤 다시 시도해 주세요."
}
```

- HTTP 상태 코드: 입력 오류 400, 인증 401, 권한 403, 없음 404, 충돌 409, 예상 못한 서버 오류 500.
- SQLite/BigQuery/Drive의 원본 오류, 토큰, 파일 전체 경로, SQL 전문은 사용자 응답에 노출하지 않는다.
- 오류 코드는 문자열 상수로 유지해 프론트가 문장 비교에 의존하지 않게 한다.
- 기존 API 응답을 변경할 경우 호출하는 React Model을 전수 검색하고 호환 필드를 유지한다.

### K-4. 저장과 외부 동기화의 자연스러운 흐름

업무 데이터 저장은 다음 순서를 원칙으로 한다.

```text
입력 검증
 → SQLite 트랜잭션으로 로컬 저장 확정
 → 로컬 응답 성공
 → BigQuery/Drive 동기화 시도
 → 성공/실패 상태 기록 및 재시도 대상 등록
```

- BigQuery/Drive 지연·실패가 SQLite 저장을 롤백시키지 않는다.
- 반대로 외부 전송을 먼저 성공시키고 로컬 저장이 실패하는 흐름도 금지한다.
- 여러 행을 저장할 때는 SQLite 트랜잭션으로 전부 성공 또는 전부 실패하도록 한다.
- 외부 동기화는 idempotent(동일 작업 재시도해도 중복 생성되지 않음) 키를 사용한다.
- 사진 저장은 로컬 파일 기록 성공 후 Drive 업로드를 수행하며, 로컬 URL·site_id·업무일자를 먼저 DB에 확정한다.

### K-5. 보호 대상 "안정 기능" 목록화

다음 기능은 수정 전 반드시 회귀 검증 대상 목록에 넣는다.

| 영역 | 보호해야 할 동작 |
|---|---|
| 인증/세션 | 로그인, 저장 세션 복구, 활성 사용자 설정, 로그아웃 |
| 유량 | 검침값 저장, 차이값 계산, 당일/월간 조회, BigQuery 동기화 |
| 수질 | 수동 저장, 외부 자료 불러오기, 사진, 분석일지 출력 |
| 약품/키트 | 입고·사용·거래명세표·사진 저장, 재고 계산, 동기화 |
| 슬러지 | 반출 사진/청소필증, 로그 기록, 파일명/Drive 전송 |
| 운전상태/일지 | 업무일자 KST 기준 저장/출력 |
| 게시판 | 세션 보호, 게시글/댓글/첨부, 새 글 표시, 정렬 |
| 설정/복원 | site_id 선택, 도로공사 복원, BigQuery 복원 전 DB 백업 |
| 업데이트 | 다운로드, 설치 잠금, 재기동, AppData 보존 |

각 영역의 라우트·서비스·테이블·외부 의존성을 `docs/ROUTE_CONTRACTS.md`에 표 형태로 작성한다. 새 기능 PR/커밋은 해당 표에 항목을 추가하거나 영향 없음이라고 명시한다.

### K-6. 변경 방지 장치

- 라우트별 최소 smoke test를 만든다: 인증 없음/잘못된 site_id/정상 저장/재조회/중복 저장/외부 전송 실패.
- 서버 시작 시 핵심 라우트가 등록됐는지 확인하는 경량 self-check를 추가한다. 실제 데이터를 변경하지 않는다.
- SQL 스키마 변경은 `database.cjs`의 명시적 마이그레이션만 사용한다. 라우트에서 임의 `ALTER TABLE` 금지.
- 공통 미들웨어·인증·site_id 결정 함수를 수정할 때는 위 보호 목록 전부를 회귀 테스트한다.
- 삭제 API는 대상 site_id와 행 존재 여부를 트랜잭션 안에서 다시 검증한다.
- 개발 편의를 위한 인증 우회/전체 현장 조회 플래그를 운영 코드에 넣지 않는다.

### K-7. 점진적 정리 순서

1. 현재 라우트 인벤토리 작성: URL, HTTP method, 인증, site_id 필요 여부, 테이블, 외부 부작용, 호출하는 React Model.
2. 중복된 인증/site_id/오류 응답 코드를 공통 미들웨어로 추출하되, 한 번에 전 라우트를 바꾸지 않는다.
3. 데이터 손실 위험이 높은 저장·삭제 라우트부터 단위/통합 smoke test 추가.
4. 동기화/사진/복원처럼 외부 부작용이 큰 라우트는 서비스로 업무 순서를 고정.
5. 기능군 단위로 마이그레이션하고, 현장 1대에서 실제 저장·동기화 확인 뒤 다음 기능군으로 진행.

### K-8. 완료 판단 기준

- 신규 라우트가 인증·입력·site_id·응답 계약을 갖추지 않으면 병합하지 않는다.
- 기존 기능을 수정하는 커밋에는 영향 라우트와 회귀 검증 결과가 남아 있어야 한다.
- 어떤 저장 실패도 "로컬 저장 실패"와 "외부 전송 실패"를 구분해 사용자·진단 로그에 나타낸다.
- 현장명 변경만으로 타 현장 데이터가 조회·수정·삭제되는 사례가 없어야 한다.
