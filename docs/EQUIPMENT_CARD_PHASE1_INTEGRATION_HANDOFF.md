# 장비이력카드 Phase 1 마무리 및 본앱 연동 인계

작성일: 2026-09-09

대상: `prototypes/equipment-history-ui/` 개발 에이전트

담당 구분(사용자 확정): 장비이력카드 개발 에이전트는 카드 UI/UX와 장비·작업사진 연결 계약을 담당한다. **일일업무일지 1·2페이지 미리보기, 장비점검표 선택/자동 판정, 날짜별 DB 저장 및 출력 연동은 이 문서를 작성한 현장관리자용 앱 담당 에이전트가 후속 구현한다.** 카드 개발 에이전트에게 일지 화면이나 점검 테이블 구현을 요청하는 문서가 아니다.

관련 문서: [기존 개발 계획](EQUIPMENT_CARD_DEVELOPMENT_PLAN.md), [레이아웃 계약](../LAYOUT_CONTRACT.md), [유지보수 지침](../POST_RELEASE_MAINTENANCE_GUIDE.md)

일지 담당 후속 검토: [날짜별 장비점검 스키마 사전 검토](DAILY_EQUIPMENT_INSPECTION_SCHEMA_REVIEW.md). 기존 테이블 재사용, 개정 저장, 동기화 충돌 및 2페이지 미리보기 연결 조건을 기록했다.

## 1. 이번 작업의 범위

현재는 **Phase 1: 독립 프로토타입 UI/UX 확정 단계**다. 라우트·DB·실제 사진 저장·본앱 이식은 이후 단계에서 구현한다. 해당 기능이 아직 연결되지 않은 것은 Phase 1의 결함이 아니다.

사용자 최신 요청은 다음과 같다.

- 장비이력카드를 작업사진관리 메뉴와 연결한다.
- 향후 일일업무일지 첫 페이지의 장비점검표와 연결한다.
- 일지 첫째·둘째 페이지를 미리보기로 확인한다.
- 장비점검에서 사용자가 양호/불량을 라디오 버튼처럼 선택할 수 있게 한다.
- 고장 장비가 있으면 해당 점검 항목에 불량을 자동 선택하는 흐름을 지원한다.
- 날짜별 점검 결과를 DB 테이블에 저장하여 다시 조회하고 출력한다.

이 문서의 데이터 구조·자동 판정 세부사항은 **연동을 위한 제안**이다. 현재 승인된 기능 방향과 구분하며, 이 문서를 근거로 Phase 1에서 서버나 DB를 변경하지 않는다. 기존 계획의 Phase 2 백엔드, Phase 3 작업사진 연결 순서를 유지하고, 일지 점검 연동은 후속 범위로 추가한다.

## 2. 기존 UI에서 유지할 부분

- 장비 목록과 상세 카드의 마스터–상세 배치.
- 공정별/종류별 보기, 공법별 카탈로그 등록, 호기별 관리번호.
- 상세 카드의 기본정보·대표사진·이력·연결된 업무사진 분리.
- Model → ViewModel → View 구조와 작업영역 내부 스크롤.
- 현장별 차이는 공법·설정·템플릿 매핑으로 흡수하는 원칙.

프로토타입 셸(main/styles/dialog shim)은 본앱에 복사하지 않는다. Phase 1에서는 메모리 Model로 상호작용을 확정하고, 이후 Model의 구현을 바꾸는 방식으로 연결한다. 다만 현장 식별자와 오류·저장 상태 계약이 추가되면 ViewModel도 필요한 만큼 변경한다. ‘Model만 바꾸면 무조건 완료’라고 가정하지 않는다.

## 3. Phase 1에서 우선 마무리할 항목

| 우선 | 항목 | 프로토타입에서 할 일 |
|---|---|---|
| 1 | 카탈로그 대수 감소 | 3→2대도 제거 대상 관리번호를 확인창에 표시. 어느 호기가 없어지는지 명확히 표시 |
| 1 | 삭제 의미 정리 | 아래 문서 충돌을 해소할 수 있도록 이력 있는 장비와 없는 장비의 UI를 구분 |
| 1 | 입력 보호 | 편집 중 배경 클릭·닫기·날짜/현장 이동 시 작성 내용 유실 방지. 변경 없으면 즉시 닫기 |
| 1 | 명시적 선택 | 목록의 선택 표시와 상세 장비 ID 일치. 검색 밖에 선택 장비가 남으면 안내하거나 선택 해제 |
| 2 | 오류 상태 | 로딩·빈 목록·검색 결과 없음·조회 실패를 별도 상태로 표현하고 재시도 제공 |
| 2 | 사진 상호작용 | 메모리 파일로 선택·썸네일·확대·추가·삭제를 확인. 서버 저장은 이후 단계 |
| 2 | 관리번호 | M-103A/B도 베이스 103으로 채번에 포함. 단일→복수 호기 전환 표기 일관성 확인 |
| 2 | 가독성 | 본문/표 13~14px 권장, 버튼 36px 이상 권장. 좁은 작업영역에서도 조작 가능 |
| 3 | 긴 이력 | 표 헤더 고정, 내부 스크롤, 연도/이력 종류 필터 검토 |

사진 개수 버튼은 실제 메모리 사진을 열도록 연결한다. 파일명만 보여주는 상태는 미구현임을 명확히 표시한다. DB 영속화까지 Phase 1에서 요구하는 것은 아니다.

### 앞선 검토의 정정 및 정책 충돌

1. 기존 계획 §3-5는 ‘체크 해제 시 제거와 연결 이력 정리’를 사용자 확정으로 적었지만, §5·§9·완료 기준은 ‘이력/연결이 있으면 RESTRICT’다. 구현 오류로 단정할 수 없으며 **문서 내 충돌**이다. 제안은 이력이 없는 잘못 등록한 장비만 삭제하고, 이력이 있는 장비는 목록에서 제외하되 이력은 보존하는 방식이다. 정책 확정 전에 연결 이력을 자동 삭제하는 동작을 영속화하지 않는다.
2. `selected = items.find(...) || filtered[0]`는 검색만 했다고 항상 첫 장비로 바뀌지 않는다. 전체 items에 기존 장비가 있으면 상세는 그대로 남는다. 실제 문제는 ‘검색 목록 밖 장비의 상세가 남음’과 ‘선택 ID가 없을 때 첫 결과를 암묵적으로 선택함’이다. 현장 데이터 혼입이 입증된 것은 아니다.
3. `숨김`은 UI에 있으나 저장 상태 목록에는 없다. 운영상태와 목록 표시 여부를 분리하는 방안을 권장한다. 숨겼다고 고장이 해소되거나 일지 점검 대상에서 자동 제외되어서는 안 된다.
4. 본앱의 기존 프리뷰와 라우트 미연결은 현 단계에서 의도된 상태다. 지금 교체하지 않는다.

## 4. 세 기능의 책임과 연결

| 기능 | 소유하는 정보 | 다른 기능에서 참조하는 방식 |
|---|---|---|
| 장비이력카드 | 장비 ID·현장·호기·사양, 고장/수리 등 이벤트 | 작업/점검에서 장비 ID로 참조 |
| 작업사진관리 | 작업일·작업내용·사진 원본/업로드 상태 | 작업기록과 장비의 연결 ID를 조회 |
| 일일업무일지 점검표 | 해당 날짜의 항목별 판정·수동 수정·판정 근거 | 장비 상태에서 초안 생성 후 날짜별 결과 저장 |
| 일지 미리보기/출력 | 확정한 같은 문서 데이터로 페이지 렌더링 | 점검 결과와 기존 일지 데이터 사용 |

장비 카드에서 ‘연결된 업무·사진’을 누르면 기존 작업기록을 열거나 해당 날짜로 이동한다. 사진을 장비 폴더에 다시 복사하지 않는다. 연결 해제와 사진 원본 삭제는 다른 행위이며 UI도 구분한다.

장비 사진과 작업 사진은 별개다. 대표사진은 `equipment_asset_photos`, 작업사진은 기존 작업기록 소유 모델을 재사용한다. 하나의 작업이 여러 장비에 관련될 수 있지만, 사진별 장비 구분이 필요할 때만 별도 연결을 확장한다. 작업 전체 사진을 특정 장비의 사진이라고 단정하지 않는다.

## 5. 지금 준비할 공통 데이터 계약

다음 이름은 프론트 DTO 제안이며 실제 SQL 컬럼명이 아니다.

```text
context: siteId, workDate
equipment: id, siteId, managementNo, name, operationalStatus, visibility
workRecord: id, siteId, date, equipmentIds[], photos[]
photo: id, ownerId, localPreviewUrl, syncStatus
inspectionItem: itemKey, label, equipmentIds[], suggestedResult,
                finalResult, source, reason, evidenceIds[]
```

- 관계 키는 장비명·관리번호가 아닌 불변 ID. 관리번호와 이름 변경 후에도 연결 유지.
- siteId는 현재 작업 창의 명시적 문맥에서 전달. admin 기본 현장이나 첫 목록 항목으로 대체 금지.
- 현장/날짜 전환 후 이전 비동기 응답이 돌아와도 새 화면에 반영하지 않는다(request sequence 등 사용).
- 선택 ID는 현장별로 관리한다. 다른 현장의 장비 ID를 연결하는 요청은 이후 서버에서도 거부한다.
- fixture도 A/B 두 현장에 동일 이름·관리번호를 준비하여 이름 기반 혼입을 검출한다.
- 저장 중 중복 클릭 방지, 실패 시 편집값 유지, 성공 시 목록·상세·연결 개수 함께 갱신.
- 실제 연동 후 빈 데이터가 오면 샘플 장비를 대신 표시하지 않는다.

## 6. 일지 장비점검 UX 제안

일일업무일지에서 현장과 업무일을 선택하면 저장된 점검 결과를 먼저 읽는다. 없으면 그 날짜 기준 장비 이력으로 초안을 준비한다. ‘점검 확인’ 영역에 항목별로 **양호 / 불량**을 같은 그룹의 라디오 버튼으로 표시한다. 그룹은 항목별 독립이며 키보드로도 선택 가능해야 한다.

- 자동 선택이면 `자동 · 수리 중인 교반기 B`처럼 이유를 짧게 표시한다.
- 사용자가 바꾸면 `직접 선택`으로 표시하며 배경 조회가 이를 덮어쓰지 않는다.
- 불량 항목에서 해당 장비/미해결 고장 및 관련 작업사진을 열 수 있게 한다.
- 자동 불량을 양호로 바꾸면 이유 입력을 권장한다. 상세 정책은 후속 UX 확정 대상.
- ‘자동 판정 다시 적용’은 변경 대상 확인 후 사용자가 요청할 때만 수행한다.
- 아직 판단하지 못한 항목은 미선택으로 표현한다. 화면 로드 성공을 실제 점검 완료로 간주하지 않는다.

### 자동 판정 규칙 제안

| 상황 | 초안 동작 |
|---|---|
| 대상 날짜에 미해결 고장/수리 중인 연결 장비 있음 | 해당 항목 불량 자동 선택 + 근거 표시 |
| 같은 항목에 장비 여러 대, 그중 한 대 불량 | 기본 제안은 항목 불량. 예비기 대체 인정 등은 현장 점검 규칙으로 분리 |
| 상태 정보 충분하고 이상 없음 | 자동 양호를 허용할 경우 ‘자동 제안’으로 표시하고 확인 후 저장 |
| 상태 이력 없음·조회 실패·장비 매핑 없음 | 미선택/확인 필요. 무조건 양호로 채우지 않음 |
| 점검 필요 또는 예비/폐기 상태 | 곧바로 고장이라고 판단하지 않음. 점검 대상 설정과 별도 해석 |
| 과거 날짜, 당시 상태를 복원할 근거 없음 | 현재 상태로 과거 판정을 만들지 않음 |
| 이미 저장된 점검 결과 있음 | 저장값 그대로 표시. 자동 재계산으로 덮어쓰지 않음 |

중요: ‘현재 수리가 완료됐다’는 이유로 어제 일지의 불량을 양호로 바꾸면 안 된다. 발생일과 완료일이 같은 경우 등 날짜만으로 순서를 판단할 수 없는 상황은 확인 필요로 표시하거나 시각 기준을 후속 설계한다.

## 7. 날짜별 점검 저장 설계 초안 — 후속 단계

기존 `facility_logs`는 개별 고장/수리 사건이고, 일일 점검표는 **해당 날짜의 점검 결과**다. 서로 별도 책임으로 유지한다. 테이블 명칭과 컬럼은 이후 스키마 검토에서 확정한다.

| 테이블 후보 | 주요 정보 |
|---|---|
| daily_equipment_inspections | id, site_id, work_date, revision, template_version, rule_version, saved_by, saved_at |
| daily_equipment_inspection_items | inspection_id, item_key, label_snapshot, suggested_result, final_result, source, reason |
| 점검 항목–장비 연결/스냅샷 | item 식별자, equipment_id, 당시 관리번호/명칭/상태, 판정 근거 이벤트 ID |

- 현장+날짜 단위 저장 계약을 정의한다. 개정판을 보존한다면 현장+날짜+revision으로 유일성을 유지하고 최신 개정 선택 규칙을 둔다.
- 헤더·항목·연결은 한 트랜잭션으로 저장. 중간 실패 시 일부만 남기지 않는다.
- 저장 후 재조회, 앱 재시작 후 복원, 과거 수정 시 변경 전후 추적을 지원한다.
- 장비 이름 변경·목록 제외·수리 완료 후에도 저장 당시 이름과 결과는 스냅샷으로 유지한다.
- 기존 일지에는 기록이 없을 수 있다. 과거 문서를 자동 변조하거나 오늘 값으로 메우지 않는다.
- 이 테이블 추가를 `facility_logs` 동기화 재사용과 혼동하지 않는다. 현재 `syncTables`에는 신규 점검 테이블 및 장비 마스터/연결 테이블이 포함되지 않으므로 BigQuery·백업/복원 지원을 별도로 설계한다.
- DB 실패 시 결과가 저장됐다고 표시하지 않는다. 편집 초안을 유지하여 재시도할 수 있게 한다.

## 8. 일지 첫째·둘째 페이지 미리보기

Phase 1에서는 샘플 두 페이지와 점검 선택 상태로 동선만 확인한다. 실제 HWP/변환 엔진 호출은 후속 단계다.

- 공통 상단에 현장명·방향·업무일을 항상 표시한다.
- 1페이지/2페이지 탭 또는 썸네일 탐색, 확대/축소, 내부 스크롤 제공.
- 점검 편집 영역과 읽기용 문서 미리보기를 구분하고, 편집 내용 반영 전에는 ‘변경 미반영’ 표시.
- 저장/반영 시 **하나의 확정 데이터 스냅샷**으로 두 페이지 미리보기와 HWP 출력을 생성한다.
- 캐시 키에 현장·날짜·데이터 개정·템플릿 버전을 포함한다. 다른 날짜/현장의 페이지를 재사용하지 않는다.
- 페이지 번호만으로 바인딩하지 않고 템플릿의 pageKey/필드 매핑을 사용한다.
- `DailyLogModel`의 기존 `preview-manifest`, `preview-page-data`와 `dailyLogPreviewService` 흐름을 먼저 검토하여 재사용한다. 기존 렌더 결과가 실제 HWP와 같은지는 별도 확인한다.
- 검침값·날씨·기온·기존 둘째 페이지 바인딩 규칙은 유지한다. 이번 기능으로 과거 날씨 조회 정책을 확대하지 않는다.
- 이미 생성된 사용자 수정 HWP는 자동 덮어쓰지 않는다. 기존 열기/재생성 정책을 따른다.

## 9. 개발 에이전트가 끝내기 쉬운 작업 순서

1. 현재 카드 UI의 삭제 대상 표시, 입력 보호, 선택 일관성, 오류 상태를 마무리한다.
2. 사진 상호작용을 메모리 fixture로 완성하고 가독성·작업영역 스크롤을 확인한다.
3. 작업사진 연결은 장비 선택 → 연결 업무 열기까지 mock callback으로 동선을 확정한다.
4. 카드 개발 에이전트는 일지 담당에게 장비 ID·현장 ID·운영상태·고장 발생/수리 완료 정보·작업사진 연결 계약과 fixture를 인계한다. 점검표와 두 페이지 미리보기의 샘플 화면 및 실제 구현은 현장관리자용 앱 담당 에이전트가 맡는다. 현재 카드 파일에 일지 로직을 합치지 않는다.
5. 사용자 UI 확정 후 기존 계획의 Phase 2/3으로 넘어간다. 날짜별 점검 저장·출력 연동은 별도 후속 작업으로 구현한다.

### Phase 1 확인 사례

- 카탈로그 3→2대 감소에서 대상 호기가 표시됨.
- 입력 중 배경 클릭으로 내용이 사라지지 않음.
- 검색/숨김/선택 장비 삭제 후 목록과 상세가 모순되지 않음.
- 사진 선택→확대→추가→삭제→편집 재진입이 메모리에서 일관됨.
- 1366×768 등 현장 화면과 좁아진 작업영역에서 글자·버튼·스크롤 확인.
- 조회 실패와 데이터 없음의 문구가 구분됨.

### 후속 연동 회귀 사례

- 양방향 동일 이름 장비, 빠른 현장/날짜 전환, 늦게 도착한 응답의 혼입 없음.
- 작업사진 장비 연결/해제 시 사진 원본과 다른 연결은 유지됨.
- 한 장비 고장 → 해당 항목만 자동 불량, 수동 선택은 재조회에도 보존됨.
- 다음 날 수리 완료 후 과거 일지 불량 유지.
- 저장→재시작→재조회와 두 페이지 미리보기/HWP 값 일치.
- 기존 검침·날씨·사진·문서 저장 규칙 회귀 없음.

## 10. 검증 및 인계 메모

검토 시 독립 프로토타입 빌드는 통과했다. 브라우저 도구에 사용 가능한 브라우저가 없어 실제 시각 검증은 완료하지 못했다. 루트 ESLint는 프로토타입을 제외하며 프로토타입 package에는 lint 스크립트가 없으므로, ‘루트 lint 통과 = 프로토타입 검사 완료’로 보고하지 않는다.

현재 단계는 프로토타입 빌드와 실제 UI 확인을 중심으로 검증한다. 전용 lint 범위는 개발 에이전트가 정리하되 기존 전체 검증 제외 정책을 임의 변경하지 않는다. 본앱 이식 시 프로젝트 지침의 validate 및 관련 진단러너 시나리오를 실행한다. 문서 전달만 하는 이번 작업에는 앱 실행·DB 변경·배포 검증을 추가하지 않는다.

인계 시 완료/미완료를 UI, 메모리 동작, 영속화, 출력 연동으로 구분하여 기록한다. 다른 에이전트가 수정 중인 본앱 파일은 동시 편집하지 않는다.
