## 2.x 목표 구조: 고정 파운데이션 + 업무 모듈

2.x는 WinForms 실행 파운데이션을 안정적으로 고정하고, 현장 업무를 독립 모듈(DLL)로 올리는 구조를 목표로 한다. 현재 안정화 버전에는 적용하지 않으며, 기존 Electron 운영을 깨지 않는 별도 전환 작업으로만 진행한다.

```text
실행 파운데이션
 ├─ 설치/업데이트/롤백, 감시런처, 진단로그, 트레이
 ├─ 인증, 현장·사용자 컨텍스트, 로컬 DB 접근, 동기화 공통 계약
 ├─ 앱 셸
 │   ├─ 왼쪽 업무 메뉴 사이드바
 │   └─ 오른쪽 워크스페이스 호스트
 └─ 업무 모듈(DLL)
     ├─ 유량관리
     ├─ 약품관리
     ├─ 수질관리
     ├─ 키트관리
     ├─ 성적서/업무일지
     ├─ 공사입력도우미
     └─ 장비이력
```

### 모듈 경계

- 파운데이션만 인증, SQLite, 파일 경로, 동기화, 업데이트와 감시런처를 직접 다룬다.
- 업무 모듈은 워크스페이스 안에서만 실행하며, 표준 계약으로 `siteContext`, 사용자 권한, API/DB 서비스, 공통 그리드, 알림, 진단로그를 받는다.
- 업무 모듈은 다른 업무 모듈의 내부 코드·테이블·화면을 직접 호출하지 않는다.
- 인증·DB 스키마·공통 API 계약을 바꾸는 변경은 모듈 단독 배포가 아니라 파운데이션 호환 버전으로 묶는다.

### 버전 및 부분 업데이트 계약

- 파운데이션과 각 업무 모듈은 각각 버전을 갖는다. 예: `foundation 2.0.0`, `flow 2.3.1`, `water 2.2.0`.
- 모듈 매니페스트에는 모듈 버전, 요구 파운데이션/API 버전, 파일 해시, 배포 시각, 롤백 대상 버전을 기록한다.
- 새 모듈은 임시 저장소에 내려받아 해시와 호환성을 검증한 뒤, 다음 앱 시작 또는 해당 워크스페이스 재진입 시 원자적으로 교체한다.
- 새 모듈의 로드·초기화 실패 시 즉시 직전 검증 버전으로 되돌리고, 파운데이션과 다른 업무 모듈은 계속 동작해야 한다.
- 현장 설정, 보고서 양식, 이미지 같은 코드 외 자산은 업무 DLL보다 먼저 독립 버전·배포 대상으로 분리할 수 있다.

### 전환 전 필수 게이트

1. 모듈 계약과 파운데이션 API를 문서·자동 검증으로 고정한다.
2. 한 업무 모듈의 실패가 로그인, 다른 메뉴, 로컬 DB, 동기화를 중단시키지 않는지 검증한다.
3. 부분 업데이트의 다운로드 실패, 전원 종료, 해시 불일치, 롤백을 현장과 같은 권한 환경에서 검증한다.
4. 기존 AppData, SQLite, 자격증명, 현장 설정을 보존한 상태로 Electron과 병행 전환한다.

## 2026년 10월 15일 운영 로그 기반 전환 백로그

운영 기준선은 Electron 1.1.54이다. 아래 항목은 .NET 전환 시 반영할 개선 계약이며, 현재 앱의 코드·DB·배포본을 변경하는 작업은 아니다. 현장 입력·로컬 저장·조회가 최우선이고 외부 동기화와 캐시 갱신은 이를 기다리게 하지 않는다. 실제 데이터 누락·동기화 장기 중단이 확인되면 전환까지 미루지 말고 현행 앱의 유지보수 대상으로 재분류한다.

### 업무 조회와 성적서 캐시 갱신 분리

- 확인 사실: 천등산 평택 2026-10-15 16:05 KST 일지 날짜 조회 약 18.5초 중 성적서 캐시 구간이 약 18.5초였고 SQL은 2ms였다. 당시 여유 메모리는 약 69%였다. 캐시 내부의 세부 병목은 아직 확정되지 않았다.
- 로컬 DB와 기존 캐시로 일지·미리보기를 먼저 표시하고, 성적서 목록 대조·다운로드는 백그라운드에서 수행한다. 최초 캐시가 없어도 일지의 다른 항목은 조회할 수 있어야 한다.
- 동일 현장·월의 갱신 요청은 하나의 작업으로 합치고, 갱신 완료 후 변경된 부분만 반영한다. 현장·월 전환이나 창 종료 뒤 오래된 결과가 새 화면에 적용되지 않도록 한다.
- 스레드 우선순위 조정이나 모든 작업의 Task.Run 전환만으로 해결하지 않는다. UI 대기 의존성을 제거하고 비동기 I/O, 제한된 작업 동시성, SQLite 쓰기 직렬화·짧은 트랜잭션을 적용한다. Node 백엔드를 재사용하면 해당 서버 대기 경로도 함께 수정해야 한다.
- 완료 기준: Drive 지연·오프라인·캐시 갱신 실패를 주입해도 로컬 일지 조회가 외부 작업 완료를 기다리지 않는다. 중복 요청·양방향 현장·날짜 전환·편집 중 갱신을 회귀검증한다.

### 데이터 동기화 실패 원인과 재시도 상태 보존

- 확인 사실: 15:30 이후 추가 수집분에서 7개 현장의 data-sync 실패 기록 17건이 확인됐다. 실패 테이블은 빈 배열이었으며, 이것은 성공이나 오탐의 증거가 아니다.
- 현재 bigQueryTriggerService는 실패 시 results 대신 error를 반환하고, backgroundSyncDiagnosticService는 이를 failed로 분류하면서 원인 메시지를 진단에 전달하지 않는다. 테이블별 실패인지 다른 실행 오류인지는 해당 기록만으로 확정할 수 없다.
- 원인 코드·마스킹된 메시지·실패 테이블·부분 성공·전송 건수·소요시간·재시도 횟수·마지막 성공 시각을 서비스부터 진단까지 유지한다. 성공·실패·사용자 활동에 따른 보류·중복 실행 생략을 구분한다.
- 원격 성공 확인 후에만 로컬 동기화 완료를 표시하며, 실패·재시작 후에도 미전송 데이터와 재시도 상태를 보존한다. 재시도는 현장 작업을 방해하지 않도록 제한된 지수 백오프를 사용한다.
- 완료 기준: 원격 오류·부분 성공·유휴 중 사용자 입력·프로세스 재시작을 시뮬레이션하고, 업무 저장 유지·실패 원인 추적·중복 없는 재전송을 검증한다.

### 공사입력도우미 세션 상태 구분

- 홍천 추가분에 세션 유지 실패 41건이 있었다. HTTP 200이어도 최종 경로가 /security/login.do이면 인증된 세션 유지 성공으로 처리하지 않는다. 실제 자동입력 실패까지 확인된 것은 아니다.
- 연결 성공과 인증 성공을 분리하고, 초기 로그인 대기·로그인 화면 이탈·인증 만료를 별도로 관리한다. 로그인 화면 이탈만으로 인증 완료를 확정하지 않는다.
- 만료 확인 시 사용자에게 재로그인을 안내하며 로컬 입력은 보존한다. 동일 만료 상태의 반복 진단은 상태 전환 기록과 누적 횟수 요약으로 제한한다.
- 완료 기준: HTTP 200 로그인 페이지, 리다이렉트, 오프라인, 정상 인증 응답, 현장별 브라우저 세션 격리를 검증한다.

### 사진 전송과 저사양 환경 운영

- 천등산 평택의 관리사진 전송은 12건 모두 성공했고 총 약 55초, 장당 약 4~6초였다. 총 소요시간만으로 장애로 분류하지 않는다. 개별 실패·재시도·완료 건수와 UI 응답성을 함께 판단한다.
- 사진 전송은 영속 큐와 제한된 동시성을 유지하고 현장 입력을 우선한다. 사용자 전송 작업에는 현재 항목과 진행률을 표시하며 준비되지 않은 분석사진은 전송 실패와 구분한다.
- 횡성 인천의 여유 메모리 8.6% 관측은 PC 전체 자원 부족 사례이며 앱 메모리 누수로 확정된 것은 아니다. 프로세스별 사용량·장기 추세로 판단하고 상태표시줄 안내는 중복 경고를 제한한다. 자동 재부팅·사용자 작업 강제 종료는 하지 않는다.
- 원격 세션 활성 상태와 실제 입력 출처는 구분한다. 현행 관찰 전용 정책을 유지하며, 새로운 차단 기능은 별도 승인과 로컬·원격 대조 검증 없이는 적용하지 않는다.

근거는 중앙관리자 전용 diagnostics.db의 drive_diagnostic_events이며, 추가 수집 범위는 imported_at > '2026-10-15 06:30:17'부터 '2026-10-15 09:15:19'까지(UTC)이다. 978개 레코드에서 동일 내용 중복을 제외한 742건을 분석했다. 이 백로그에는 운영 로그 원문·비밀번호·자격증명을 복사하지 않는다.
